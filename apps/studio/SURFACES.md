# Floating surface rules

The original contract is in `src/shared/types.ts` (SurfaceWindow/SurfacePlan), `src/worker/surfaces/surface.ts`, and `src/client/components/SurfaceLayer.tsx`.

Studio implements that contract with `flexlayout-react` float sublayouts in `components/FloatingPanels.tsx`. Every visual surface goes through this layer, including website/PDF/3D/video/timeline previews and research images/articles/source lists. Do not add fixed-position one-off panels, dashboards or navigation.

- Speech answers; a panel shows persistent information that benefits from seeing, comparing or manipulating it. Open panels for requested previews, attached documents, generated/edited visual artifacts, research source evidence and image/article context. Plain conversation does not need a panel.
- Use stable IDs. Update an existing result in place and preserve its position and size. Different results can coexist. Close only on user dismissal or an explicit close request.
- Keep floating rectangles inside the viewport when its size changes. Fit the saved preferred rectangle to the available bounds, restore it when space returns, and retain deliberate user moves made at the smaller size. Model adoption preserves matching tab view state during these adjustments, including unsent input in an open window.
- Panels float, drag, resize, stack, tab and dock through FlexLayout. The conversation beneath stays interactive. Do not open native browser popout windows.
- The local Work history window records every specialist job, its full request, progress, specialist summaries and outcome. Say “show work” to open it. Closing the page leaves local jobs running; reopening restores the history. Explicit Stop cancels a task. A backend restart marks unfinished specialist jobs interrupted for review, because replaying document edits without a checkpoint could duplicate writes. Software builds retain their separate resumable checkpoints and Software work window.
- Unsuccessful terminal Work cards expose **Edit saved request** only when their host supplies the callback. Pass the complete saved record unchanged. Preparation restores editable text and its website/PDF context in the existing composer for an explicitly submitted new attempt; it must not auto-submit, claim checkpoint continuation or overwrite an unsent draft. Keep the old outcome and history visible, with pending and rejection messages on the affected card. **Setup instructions** reuses the existing native Download dialog.
- Keep model and voice readiness separate in the existing orb setup area and installation dialog. Model ready means the local service answered its health check; voice ready means initialization succeeded for the page. Unknown, unavailable and checking states remain explicit, and initialization must not imply microphone access, spoken-reply verification or task quality. A changed explicit setup request opens the existing native dialog once; quiet readiness updates and repeated request tokens must not reopen it or reset focus.
- The local Goals window shows coordinated work across a planner, specialist executors and a separate acceptance reviewer. Say “show goals” or “plan this goal: …” to open it. It displays the saved goal, milestone dependencies, host execution evidence, acceptance decisions and recorded role activity. Goals continue while the window or page is closed; pending or interrupted work remains visible after restart. Public research is an explicit option, and an open PDF can be included. Stop preserves the plan; continuation keeps accepted milestones and retries unfinished work with optional guidance. This window uses the stable `coordinated-goals` surface ID and stays separate from public collaboration goal discovery.
- Software milestones expose an explicit child-build link supplied by the host, including active builds. **Open software build** opens the existing Software work window, loads the specific saved build even when it is outside recent history, and highlights it with its screenshots, checks and available downloads. The Goals window keeps its position. Never derive child identifiers from model summaries or arbitrary evidence strings.
- Completed builds expose a **Revision guidance** form, limited to 2,000 characters. **Create revised build** selects a distinct child in the same stable Software work window. Render the host's `parentTaskId`, `parentRevision` and `revisionNote` as the parent link and requested revision; keep the accepted parent's downloads accessible through **Open parent build**. Child checks, screenshots and downloads follow the child's own status and evidence, with fresh verification before release.
- Paused or cancelled software builds expose optional **Guidance for continuing** with a 2,000-character limit. Resume sends that note through the existing resume API and also works with no note. Display persisted `latestGuidance` separately from the original `revisionNote`; pending actions, success and errors belong to the affected build card.
- Software cards lead with current status, activity and parent lineage. Use the requested revision as a short child heading. Long saved requests stay behind **Full saved goal**, which fetches the exact request from the task detail API; the bounded recent-history summary is not the full goal.
- Goals, Work and Software use the shared native **ActivityHistory** disclosure for saved timelines. Fetch the first page only when opened; **Show earlier activity** uses sequence cursors and preserves loaded entries without duplicates. Live card polling must keep the reader's snapshot and scroll position. **Refresh activity** replaces that snapshot only after a successful response. Errors retain loaded history and provide retry; closing, switching streams or unmounting aborts pending requests and rejects late results.
- Activity rows show saved date/time, role, phase, detail and any supplied milestone or revision. Keep the list inside a bounded scrolling region. Identify imported retained history and explicitly state when older events may already be missing; do not claim discarded events were recovered. Resource loaders retain their existing access rules, including the Software builder's paired origin and private headers.
- Show the reason a panel was raised; never steal microphone/input focus for quiet updates. As panel count grows, reduce attention rather than silently discard requested results. Original host bounds are 6 windows per turn and 12 open; refusal must be explicit.
- Render only host-controlled components. Research HTML is data, never executed. Show actual source links, publisher/date, image credit/license and whether imagery is background or a verified event photograph. Images require descriptive alt text.
- Retrieval panels can appear before reasoning and speech finish; image retrieval must not block the spoken answer. An article preview uses sourced text/link, not an arbitrary iframe that publishers may block.
