# First-use recovery: accepted work, failed delivery and explicit new attempts

Research date: 2026-10-29. This is a research-only plan: no core/UI files, backend state, browser, port 3211, credentials or service configuration were changed. It does not provision a model or alter the existing Hugging Face HTTP 403 restriction. Exact fetched URLs, local files and SHA-256 hashes are archived in `primary-sources.json`; `sources.json` also records unavailable requests. The RFC Editor endpoint returned the network proxy’s HTTP 403, while the official HTTP Working Group’s published RFC 9110 source and rendered RFC were available over normal verified TLS.

## Primary sources and applicable rules

1. [WHATWG Fetch source](https://raw.githubusercontent.com/whatwg/fetch/main/fetch.bs), `fetch()` algorithm and “consume body” / “abort the fetch() call”: a network error rejects the Fetch promise; other responses resolve to a Response object. Body consumption and streaming can fail separately, including after the initial response has been delivered. Aborting an already fulfilled Fetch promise does not unfulfill it, although its response body can be errored.
2. [WHATWG DOM source](https://raw.githubusercontent.com/whatwg/dom/main/dom.bs#L1854), “Aborting ongoing activities”: AbortController changes an AbortSignal and supporting APIs decide how to react. It does not define transactional rollback of an application’s already accepted task or mutation.
3. [RFC 9110 official HTTPWG source](https://raw.githubusercontent.com/httpwg/http-core/main/rfc9110.xml), §9.2.2 “Idempotent Methods”; [official rendered RFC](https://raw.githubusercontent.com/httpwg/httpwg.github.io/main/specs/rfc9110.html): automatic retry of a non-idempotent method requires known idempotent application semantics or a way to determine the first request was never applied. A failed response alone does not establish either. Task-creating POST requests have no general automatic-retry guarantee.
4. [React controlled-input documentation](https://raw.githubusercontent.com/reactjs/react.dev/main/src/content/reference/react-dom/components/input.md), “Controlling an input with a state variable”: the value is the rendered source of truth, and onChange synchronously updates that state. Keep submitted text as an explicit snapshot; clearing the controlled value clears the user’s visible draft.
5. [React useEffect documentation](https://raw.githubusercontent.com/reactjs/react.dev/main/src/content/reference/react/useEffect.md), data-fetching cleanup example: responses can arrive out of order. Cleanup/operation guards prevent stale completions from overwriting current state. Development Strict Mode also exercises setup/cleanup twice, so mounting or restoring a draft must not itself submit a task.

## What a failure establishes

- **Fetch rejects, or an abort/JSON/body failure prevents reading an acceptance receipt:** the browser did not obtain a usable acknowledgement. The server might never have received the POST, or might have accepted it before response delivery failed. Keep the draft and say acceptance is unconfirmed. Do not invent a task ID, claim nothing was created, classify it as a saved failed task without a real row, or automatically replay the POST.
- **An HTTP error response arrives:** Fetch itself can resolve normally. The client must check status and the application response. A documented validation rejection can establish rejection, but a generic HTTP error status alone does not prove no prior application effect.
- **A valid acceptance response supplies a real saved task ID:** treat task acceptance as its own completed stage. A later speech/playback/stream error does not revoke that ID or establish that the task failed. Keep the task link and retrieve its actual status. If native inference subsequently fails, the backend’s durable failed record establishes that task failure independently of speech delivery.
- **The UI aborts a fetch or unmounts:** local observation stopped; accepted work was not thereby undone. Task cancellation requires the existing explicit Stop operation and its real saved status. Never turn an observation or audio failure into an implicit stop/replay.
- **A destination returns a proxy HTTP 403, or the local inference server cannot be reached:** record the specific observed operation/error. This does not establish missing credentials, justify a duplicate secret request, prove all network access is broken, or show that replaying a user task will work.

## Smallest supported recovery workflow

Keep Goals and Software checkpoint continuation unchanged. A terminal Work record has a saved original request, project and optional PDF; it does not contain a resumable orchestration checkpoint. Offer **Edit saved request** to open the complete saved text for editing. Editing is local preparation. A separate explicit Send creates a new task/attempt through the existing guarded submission route. The original record, outcome, ID and activity history stay unchanged. Do not call this “resuming” the old Work task.

Restore or explicitly bind the original project/PDF context before a mutation can be resubmitted. If that context is unavailable, retain the text and explain what must be selected rather than sending it against a different current project. Reuse only data actually saved for this workflow; do not restore secret values, inferred tool permissions, or a fabricated checkpoint.

Keep an exact submitted-draft snapshot until acceptance is known, separate from any newer text the user types while the request is pending. A late error must not overwrite a newer draft, and a late success must not clear newer text or apply its status to another attempt. If editing a saved request would replace an existing unsent draft, preserve that draft separately or let the user explicitly choose replacement. No additional automatic task creation is needed.

## Concrete acceptance criteria

1. **Full draft retention:** enter a supported long request with a distinguishing final sentence. A pre-acceptance rejection or transport/JSON failure leaves the full submitted text recoverable. Re-rendering does not reduce it to a status-label excerpt. No fake durable Work row or task ID is generated on the client.
2. **No hidden replay:** opening Edit saved request, editing, focusing, closing/reopening history, and effect setup/cleanup cause zero task-creation POSTs. Only the explicit Send creates a new attempt. Do not resubmit after a timer, fetch error, speech error, reload, or Strict Mode cleanup.
3. **Honest ambiguous delivery:** test a POST that the server accepts before response delivery is lost. The UI labels acknowledgement as unconfirmed, keeps the text and directs the user to saved work. It does not assert that no task exists or automatically create a second one. Matching old requests by text alone is insufficient to prove which acknowledgement was lost.
4. **Accepted-task/audio separation:** accept a real task ID, then fail speech or streamed delivery. The real ID stays available and the UI shows the audio/delivery problem separately. Poll the task’s actual saved running/completed/failed status; no duplicate task and no implicit cancellation occur.
5. **Explicit new Work attempt:** select a terminal record, open its full saved request and original target, change the request, and Send once. A distinct real task ID is returned. The old task’s source record, terminal outcome and durable activity history remain unchanged; new activity belongs to the new ID. Goals and Software retain their existing checkpoint controls.
6. **Target and draft safety:** repeat editing while another project/PDF is selected and while a different unsent draft exists. No request silently targets that unrelated workspace, and neither the current draft nor the recovered saved request is lost. Missing original targets leave an editable request with a clear blocking explanation.
7. **Out-of-order results:** type new text while an older attempt is pending, then resolve/fail the older operation. Its handler cannot clear or replace the newer text. An older operation’s errors cannot overwrite the current attempt’s status.
8. **Native first-use measurement:** with the actual model unavailable, verify the real accepted/terminal Work record, its full recoverable request, explicit edit path and truthful model/speech error states. This validates recovery behavior, not real inference capability, model provisioning, speech synthesis or unrestricted task competence. Transport-loss fixtures may supplement this audit but must be identified as fixtures.

No automatic replay, new checkpoint service, secret setup or model fallback is required for this recovery improvement.
