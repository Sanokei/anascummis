# Source-kit handoff research and observations

The real human objective in this task is to keep improving the same application, its specialist orchestrators and visible persistent work. The existing repository installation/distribution contract is a local source kit, with manual prerequisites, CPU runtime setup and separate model/app processes. It does not promise a prebuilt installer or every-device support. Those constraints were retained; no new installer format or native platform guarantee was inferred.

At base 7fabdbb, DownloadLocal points to an unversioned external ZIP. A normal build does not create a source kit under the ordinary server's output. The old publisher only writes `.demo-assets/opensource`, without a source/version/file manifest. A normal HEAD to the public URL returns proxy 403, so its actual bytes and deployed revision remain unknown. This is not evidence that the live ZIP is definitely stale; the missing local handoff and absent identity were reproduced separately.

The publisher already includes app sources, its Bun lockfile, the standalone shared-types adaptation, existing license files, LavaSR source/license, and Etro 0.14.1's corresponding source. Preserve those inputs while excluding actual state, environments, credentials, caches and model/runtime binaries. Current-source and archive checks verify those properties against the produced kit rather than treating a successful ZIP write as sufficient.

The installed Next 16.4.3 package declares Node>=20.9.0, and its CLI starts with `#!/usr/bin/env node`. This supports the added Node prerequisite for the existing build command. Bun's actual install help confirms `--frozen-lockfile` disallows lockfile changes. The validation reuses matching already installed dependencies and Python; it does not claim a fresh online installation or successful native-model/voice setup.

Two observations from the first extracted build needed correction. Reopening the modal retained its previous middle scroll position and clipped a later unavailable-kit warning. Reset that scroll region on explicit open and show the requested kit action before secondary setup content. Removing only the owned extraction's ZIP while leaving its manifest reproduced a link that remained advertised despite a real503. The final dialog checks the versioned same-origin artifact with HEAD before enabling Download. It checks status, ZIP-compatible media type and length when supplied; it does not pre-download ZIP bytes or models.

The ordinary Bun static response omits Content-Length on HEAD. RFC 9110 §8.6 permits Content-Length in HEAD and constrains its value when supplied; §9.3.2 says a server may omit header fields determined only while generating content. Treat a missing length as unknown, not a failed archive. The actual explicit browser download is separately SHA-256 verified, and a clean extracted build reproduces exactly the same ZIP bytes. The official HTTPWG source was already cached from a verified-TLS retrieval and was reused without another download. Exact URL/hash and repository/dependency references are recorded in sources.json.

The source version is a hash of the sorted public payload inventory, declared source provenance and dependency versions. The ZIP has a separate SHA-256. Artifact-only Git commits do not relabel unchanged application source; clean extraction preserves its declared source metadata only when the payload inventory matches. These hashes identify content and support comparison, not code-signing/authenticity guarantees. No private state or downloaded models are needed to build the same application and observe its honest unavailable-service path.
